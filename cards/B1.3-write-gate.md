## Summary
- What is wanted: a hook that lints the PENDING write (the file as it would
  land, not the file as it is) against the doctrine's banned patterns, and
  reports. Advisory by default: the report is a steering signal, the author
  self-corrects. Under a strict switch, the same lint blocks before the write
  lands, exiting 2 with the three-part message.
- Why it matters: a red gate is a steering signal, and the refusal itself
  re-injects the law at the moment of violation — the message is the
  enforcement.

## Context
- The gate lints overlays (the pending change), never the whole tree; it is
  fast, deterministic, and has no model in the loop.
- The three-part refusal message: (1) what happened, one line naming the
  file and the violated rule number; (2) the pointer, the canonical section
  to read; (3) the hatch, the logged override path for the audited escape.
- Fixture vocabulary for this card, verbatim: `TODO`, `FIXME`,
  `temporarily disabled`, `skip: true`.
- Guidance: "The Enforcement Pipeline" (the hook ladder; the return channel);
  "Dura Lex, Sed Lex" (the rejection as the second injection; the audited
  door).

## Failing test
- Test file / class: `tests/test_write_gate.py::TestAdvisoryAndStrict`
- Guarantee it asserts: (a) a clean pending write exits 0 silently in both
  modes; (b) a violating pending write in default mode exits 0 and prints a
  REPORT line naming file and rule number; (c) the same write under
  `DOCTRINE_GATE_STRICT=1` exits 2 and prints the three-part message; (d) the
  override, when used, is logged (an append-only line with timestamp, rule,
  and file).
- Command: `python3 -m pytest tests/test_write_gate.py -q`
- exact failure on the base commit (when the red test is run before
  `scripts/doctrine-write-gate.sh` exists): exit code 1,
  `FileNotFoundError` / `AssertionError` (`scripts/doctrine-write-gate.sh`
  not found).

## Mutants
- M1 (fail-open): strict mode exits 0 on a violating write.
  `TestAdvisoryAndStrict::test_strict_blocks` must turn red.
- M2 (silent advisory): default mode prints nothing on a violating write.
  `test_advisory_reports` must turn red.
- M3 (unlogged hatch): the override is accepted but not appended to the log.
  `test_override_logged` must turn red.
- M4 (whole-tree linter): the gate flags a banned pattern that exists in the
  tree but not in the pending overlay. `test_lints_pending_not_tree` must
  turn red.

## Doctrine
- Principles engaged: the local hook ladder, every rung returning text into
  the author's context; advisory by default, blocking on demand; the audited
  escape hatch.
- Why this validation is sufficient: every quiet-failure mode of a gate
  (fail-open, silent report, unlogged bypass, scope creep) is a named mutant.

## DESIGN SELF-CHECK
1. Claims and pins: pending-overlay, advisory, strict and override claims
   map to (a)-(d); no claim makes the default advisory a blocking gate.
2. Constants: fixture vocabulary, strict switch and three-part message shape
   have one source; tests do not paraphrase them.
3. Shared state and test order: pending-write fixtures are independent;
   override-log assertions run only after the explicit override action.
4. Inherited environment: gate fixtures set the strict switch explicitly
   and remove inherited git repository variables.
5. Mutant kills: M1-M4 name their tests; clean pending input is the green
   control in both modes.
6. Composition: B1.1 supplies the rule index; B1.4 invokes this one gate;
   B4.2 consumes its evidence without another linter.
